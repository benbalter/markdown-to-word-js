# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Browser app that converts Markdown to Word documents, live at [md2word.app](https://md2word.app). An [Astro](https://astro.build) static site on Cloudflare Workers Static Assets, built as the mirror image of [word2md.com](https://github.com/benbalter/word-to-markdown-js): same design, layout, and conventions. See [CONTRIBUTING.md](CONTRIBUTING.md) for setup.

## Commands

Run these before pushing. They match [ci.yml](.github/workflows/ci.yml):

```sh
npm run lint        # eslint, check only (lint:fix rewrites files)
npm run typecheck   # tsc over web/, src/, test/, scripts/, and configs
npm test            # vitest unit tests
npm run build       # astro check + astro build into dist/, plus SEO/a11y checks
npm run test:e2e    # Playwright against dist/; build first
```

One file or one test: `npx vitest run test/docx-structure.test.ts`, `npx vitest run -t "<test name>"`, `npx playwright test test/e2e/csp.spec.ts`. The e2e tests drive installed Google Chrome (`channel: 'chrome'` in [playwright.config.ts](playwright.config.ts)), not Playwright's bundled Chromium.

## Layout

- [`web/`](web) is Astro's `srcDir`: pages, layouts, components, styles, and the i18n dictionaries. [`web/site.ts`](web/site.ts) is the single source of truth for the domain.
- [`src/`](src) is the converter (Markdown → HTML → .docx) plus [`src/index.ts`](src/index.ts), the browser entry that wires up [`Converter.astro`](web/components/home/Converter.astro). Element ids and `data-*` attributes are the contract between those two files.
- `src/` minus `index.ts` is also the [`markdown-to-word`](https://www.npmjs.com/package/markdown-to-word) npm package: [`src/main.ts`](src/main.ts) is its public API, and [`src/node.ts`](src/node.ts) its Node entry, which fills in `DOMParser`/`XMLSerializer` from jsdom. [`tsconfig.build.json`](tsconfig.build.json) builds it into `build/` (`npm run build:lib`). [`src/cli.ts`](src/cli.ts) is its `md2w` / `markdown-to-word` command, built on the Node entry. Anything exported from `main.ts` is public API, so changing it needs a semver bump.
- Conversion runs entirely in the browser. Keep it that way, and keep the converter `import()`ed lazily: html-to-docx is the page's biggest chunk, so it stays off first paint. (Browsers with the [offline service worker](#deploying) still download it once, after load.)

## Conversion pipeline

[`convertMarkdownToWord`](src/converter.ts) runs four stages, and the converter tests check the result by reading the .docx back into HTML with [mammoth](https://github.com/mwilliamson/mammoth.js):

1. [`parseMarkdownToHtml`](src/markdown-parser.ts): marked, GFM, plus [marked-footnote](https://github.com/bent10/marked-extensions/tree/main/packages/footnote). `extractTitle` lexes with a second instance without it, because lexing without rendering corrupts that extension's per-document state. If the HTML has images, [`embedImages`](src/docx-images.ts) then fetches each one once into a `data:` URI, so html-to-docx doesn't download it again, and swaps any it can't fetch for its alt text. The page preview uses `renderPreviewHtml`, the same HTML passed through DOMPurify. The .docx path skips DOMPurify because html-to-docx never runs the HTML.
2. [`prepareHtmlForDocx`](src/docx-html.ts) rewrites what [html-to-docx](https://github.com/turbodocx/html-to-docx) would drop: rules become `RULE_TEXT` paragraphs, task-list checkboxes become glyphs, block quotes become indented paragraphs, unknown inline tags (`<kbd>`, `<abbr>`) become spans, footnote links are unlinked, and styles ride in `data-docx-style` because the CSP blocks `style` attributes even inside `DOMParser` documents.
3. html-to-docx generates the .docx. [`buffer-global.ts`](src/buffer-global.ts) must be imported before it, or images break.
4. Three post-generation patches rewrite the .docx XML with JSZip: [code blocks](src/docx-code-blocks.ts), [structure](src/docx-structure.ts) (rules, table header rows, moving `<w:sectPr>` to the end of the body, and declaring a content type for every embedded image format), and the optional [font preset](src/docx-font-preset.ts). Each one runs only when the HTML needs it (the structure patch, for every document), is `import()`ed lazily, and goes through `patchOrKeep`, so a failed patch returns the unpatched document instead of failing the conversion.

The patches find their paragraphs by matching, in order, against counts and texts taken from the source HTML. So when you change what stage 1 or 2 emits, update the patch that matches it.

## Rules the build enforces

- **CSP:** a strict Content-Security-Policy ships as a `<meta>` tag ([`astro.config.mjs`](astro.config.mjs)). Never use `style="…"` attributes (use classes, or `element.style` from JS) or `<script is:inline>` (Astro only hashes scripts it bundles). Pass server values to scripts through `data-*` attributes.
- **No HTML comments in `.astro` files:** Astro ships `<!-- -->` verbatim. Use `{/* */}`.
- **i18n:** every string lives in [`web/i18n/en.json`](web/i18n/en.json), typed by [`types.ts`](web/i18n/types.ts). English is the source; the other 20 locales (the same set as word2md.com, including right-to-left Arabic) are listed in [`locales.ts`](web/i18n/locales.ts), and [`web/i18n/README.md`](web/i18n/README.md) covers adding more.
- **Design:** follow word2md's [DESIGN.md](https://github.com/benbalter/word-to-markdown-js/blob/main/DESIGN.md) (tokens in [`web/styles/global.css`](web/styles/global.css)): one filled accent button per screen, chartreuse only on the output or the next action.

## Agents and crawlers

[`web/agent/markdown.ts`](web/agent/markdown.ts) builds Markdown for machines from the same sources the HTML renders (`web/i18n/en.json`, the `legal` and `guides` collections): `/llms.txt` and `/llms-full.txt` ([`web/pages/llms*.txt.ts`](web/pages)) and a Markdown twin of every English page ([`web/pages/[page].md.ts`](web/pages/[page].md.ts): `/index.md`, `/privacy.md`, `/terms.md`). Don't hand-edit copies in `public/`. Layout advertises a page's twin with `<link rel="alternate" type="text/markdown">` (the `markdownPath` prop), and the Worker serves it for `Accept: text/markdown`. The English-only task pages (`/chatgpt-to-word/`, `/markdown-tables-to-word/`, `/developers/`) are Markdown in [`web/content/guides/`](web/content/guides), rendered by [`Prose.astro`](web/layouts/Prose.astro) with TechArticle JSON-LD, linked from the footer, and given no hreflang. A new English page with a twin goes in `agentPages()` and in `run_worker_first` in `wrangler.jsonc`; [`test/agent-markdown.test.ts`](test/agent-markdown.test.ts) checks the two agree, and [`test/e2e/agents.spec.ts`](test/e2e/agents.spec.ts) checks the generated files and the JSON-LD. [`public/robots.txt`](public/robots.txt) sets `Content-Signal: search=yes, ai-input=yes, ai-train=yes`, a deliberate choice to welcome AI use.

Agents can also _convert_, always locally, so "nothing is uploaded" stays true: `md2w mcp` ([`src/mcp.ts`](src/mcp.ts), loaded by a dynamic import in `src/cli.ts` so conversions never load the MCP SDK) is a stdio MCP server with a `convert_markdown_to_word` tool. An agent may be acting on untrusted instructions, so the tool reads only Markdown files and writes only `.docx` files, opens the output with `O_NOFOLLOW` and (unless `overwrite: true`) `O_EXCL` so it never writes through a symlink or clobbers a file, and never fetches remote images, which stay alt-text links (the converter has no option for that, so a global `fetch` that always fails, plus a `console.warn` wrapper, report per call through `AsyncLocalStorage`). As defense in depth, the server also refuses every outbound TCP connection (`net.Socket.prototype.connect`), because html-to-docx bundles its own HTTP client: today it downloads through the global `fetch`, but an upgrade could change that. An opt-in fetch with an IP blocklist was tried and dropped: DNS rebinding defeats a resolve-then-fetch check. Keep those limits; `test/mcp.test.ts` checks each one. [`test/mcp.test.ts`](test/mcp.test.ts) drives it end to end over stdio and [`test/cli.test.ts`](test/cli.test.ts) runs the CLI, both against `build/cli.js`, which the Vitest global setup ([`test/build-cli.ts`](test/build-cli.ts)) rebuilds when it's stale; the two files are excluded from coverage because they only run in child processes. In the browser, [`web/scripts/webmcp.ts`](web/scripts/webmcp.ts) registers a WebMCP tool, `convert_markdown_to_docx`, that goes through the page's own `convert()` in `src/index.ts`, shows the result, and returns the .docx as base64 (its download attempt is best effort). [`test/e2e/webmcp.spec.ts`](test/e2e/webmcp.spec.ts) stubs `document.modelContext` to test it. Neither ever adds a server-side conversion endpoint. For Claude Desktop the server also ships as a one-click MCP Bundle, `markdown-to-word.mcpb`: `npm run pack:mcpb` ([`scripts/pack-mcpb.mjs`](scripts/pack-mcpb.mjs)) builds and smoke-tests it, with a `manifest.json` from [`scripts/mcpb-manifest.mjs`](scripts/mcpb-manifest.mjs) whose tools come from the server's own `tools/list`, and [`mcpb.yml`](.github/workflows/mcpb.yml) attaches it to each GitHub Release.

## Deploying

- [`worker/index.js`](worker/index.js) runs only for `/`, the English pages with a Markdown twin, and `/api/event` (`run_worker_first` in [`wrangler.jsonc`](wrangler.jsonc)). A request whose `Accept` prefers `text/markdown` gets the page's twin, ahead of everything else (see [Agents and crawlers](#agents-and-crawlers)). Otherwise it redirects first-time visitors on `/` to their Accept-Language locale and tags the English page for the "also available in" banner. Everything else is a static asset.
- **Conversion counter**, ported from word2md.com: after each conversion, [`web/scripts/analytics.ts`](web/scripts/analytics.ts) sends a content-free, fire-and-forget beacon (`POST /api/event?o=<success|error>&l=<locale>&s=<source>[&e=<kind>]`), only on `SITE_HOST`, so local and self-hosted copies send nothing. The Worker checks it's same-origin, bounds every value (anything else becomes `other`), and writes one Analytics Engine data point, `blobs: ['convert', outcome, locale, source, errorKind]` (`errorKind` is `none` on success), to `md2word_events` (previews: `md2word_events_preview`). The sources live in [`web/scripts/conversion-sources.ts`](web/scripts/conversion-sources.ts), shared by the beacon and the Worker: `drop` (a `.md` file dropped or chosen), `paste` (Markdown pasted or typed, converted with the button or Ctrl/⌘+Enter), `webmcp` (the `convert_markdown_to_docx` tool). Error kinds live in [`web/scripts/conversion-errors.ts`](web/scripts/conversion-errors.ts) (`load`, `too-complex`, `conversion`), picked by `classifyConversionError`, which also picks the message shown, so the two agree. It counts once per attempted conversion in `convert()`, not per download or copy; input refused up front (a Word file, too large, binary, an empty box) and superseded conversions aren't counted. Never add content, a filename, a size, or an identifier, and append new dimensions as `blob6`… so saved queries keep working. Weight queries by `_sample_interval` (Analytics Engine may sample). By source: `SELECT blob4, SUM(_sample_interval * double1) FROM md2word_events WHERE blob1='convert' GROUP BY blob4`; by error kind: `SELECT blob5, SUM(_sample_interval * double1) FROM md2word_events WHERE blob1='convert' AND blob2='error' GROUP BY blob5`; more in [docs/cloudflare.md](docs/cloudflare.md#conversion-counter). The [privacy policy](web/content/legal/privacy.md) discloses it, and [`test/e2e/conversion-beacon.spec.ts`](test/e2e/conversion-beacon.spec.ts) serves the build as md2word.app through `page.route()` to check each source's beacon.
- **Offline service worker:** md2word.app is installable ([`public/manifest.webmanifest`](public/manifest.webmanifest); `npm run gen:icons` renders its icons from `favicon.svg`) and works offline after a first visit, ported from word2md.com. The `serviceWorker()` integration in [`web/pwa/service-worker.ts`](web/pwa/service-worker.ts) writes `dist/sw.js` after each build from the [`web/pwa/sw.js`](web/pwa/sw.js) template, precaching every hashed `/_astro/*.js` chunk: the page script, the parser, html-to-docx, and the three .docx patches, which must be precached because `patchOrKeep` would otherwise quietly ship an unpatched document offline. [`PwaRegister.astro`](web/components/PwaRegister.astro) registers it. Navigations stay network-first so `/` and the twin pages still reach the Worker; only `/_astro/` is cache-first; `/api/`, non-GET, and cross-origin requests (a document's remote images) pass through, so offline images fall back to alt text. A new version waits for old tabs to close (no `skipWaiting`). `/sw.js` is served `no-cache` ([`public/_headers`](public/_headers)), and neither it nor the manifest may go in `run_worker_first`. To retire it everywhere, set `serviceWorkerKillSwitch = true` in [`web/pwa/config.ts`](web/pwa/config.ts) and push: the build then ships [`web/pwa/sw-kill.js`](web/pwa/sw-kill.js), which clears the caches and unregisters itself on every device. The e2e config blocks service workers (they'd bypass `page.route()` mocks); [`test/e2e/pwa.spec.ts`](test/e2e/pwa.spec.ts) opts back in and converts offline, and [`test/service-worker.test.ts`](test/service-worker.test.ts) pins the rules.
- Pushing to `main` is a production deploy: Workers Builds runs `npm run build && npm test`, then `wrangler deploy`. Branches get preview URLs. See [docs/cloudflare.md](docs/cloudflare.md).
- Push or merge to `main` only when the owner says to, and never run `wrangler deploy` yourself.
- Publishing a GitHub Release publishes to npm ([release.yml](.github/workflows/release.yml); steps in [CONTRIBUTING.md](CONTRIBUTING.md#releasing-to-npm)). Never create a release, a `v*` tag, or run `npm publish` without the owner's OK.
